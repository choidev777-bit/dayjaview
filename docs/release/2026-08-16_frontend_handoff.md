### 2.1 새로 만든 화면 3개

`screen_spec`의 과거 영역 화면이 비어 있어 시안 구조에 맞춰 채웠다.

**같은 검증에서 추가로 찾은 것** — 당시 주도 종목이 전부 `0.0%`로 나오고 있었다. `market.prices_daily`에도 같은 (종목, 날짜)가 **50만 행 중복**이라 최근 2거래일 종가를 뽑으면 같은 날이 두 번 잡혔다. 날짜당 한 행만 쓰도록 고쳤고(대한광통신 0.0% → +22.5%), 가격을 못 찾은 종목은 0%로 적지 않고 목록에서 뺐다 (`screen_spec` 8.9 `계산 불가는 —, 0 표시 금지`).

> **DB를 쓰실 때 주의** — 구 DB의 `engine.event_outcomes`와 `market.prices_daily`는 둘 다 같은 키가 두 벌씩 들어 있다. 그냥 join하면 건수와 수익률이 모두 부풀려진다.

### 4.2 시연 데이터의 한계 (반드시 알고 볼 것)

- 수익률은 구 DB 종가 기준 **동일가중**이다. 정본(상한형 유동시총 가중)이 아니다. 계약상 `weightMethod` 값에 다른 선택지가 없어 `FREE_FLOAT_CAPPED`로 들어가 있으나, `legacyDemo.json`의 `weightMethod`는 `EQUAL_WEIGHT_LEGACY`로 표시해 두었다.
- 그래서 **테마 상세의 계산 기준 문구는 시연 데이터에는 맞지 않는다.** 실제 파이프라인 값이 들어오면 그대로 맞는다.
- T+1/T+5/T+20은 구 DB `engine.event_outcomes`에 이미 계산돼 있던 값을 그대로 쓴다.
- 기준일은 2026-08-10(전일 2026-08-07)이다.

### 4.3 결정이 필요한 것

**실시간 트리맵 색이 전부 같아 보인다.** `realtime_theme_treemap_implementation_plan` §5.2가 색상 강도를 `min(|수익률| ÷ 5%, 1)`로 정해 두었는데, 8월 10일 상위 10개 테마가 전부 +7.4~+10.4%라 모두 5%를 넘어 강도가 1로 포화된다. 즉 규칙대로 동작한 결과다.

면적은 규칙대로 정확히 비례한다(실측: 면적비 1.40 vs 수익비 1.41). 차이가 작아 보이는 것은 최대/최소가 1.4배뿐이라 한 변 기준으로는 1.19배이기 때문이다.

선택지는 셋이다.

1. 포화 기준을 5% → 15%로 올린다. 절대 기준이라 같은 수익률은 언제나 같은 색이라는 성질은 유지되고, 오늘 같은 날에도 농담이 갈린다. **§5.2 숫자를 고쳐야 한다.**
2. 그대로 둔다. 평범한 날에는 농담이 갈리고, 오늘처럼 모두 강한 날은 `전부 강함`이 색으로 드러나는 것이 의도된 동작이라고 설명한다.
3. 그날 범위로 상대 정규화한다. 항상 대비가 생기지만 같은 +8%가 날마다 다른 색으로 보여 금융 화면에서는 권하지 않는다.

현재는 **2번(그대로)** 상태다. 판단 부탁드린다.

### 4.4 배포

- `main`에 올려 뒀으나 Vercel 자동 배포가 걸려 있지 않다. 배포된 번들과 로컬 빌드 산출물이 다르다.
- 백엔드는 살아 있고 `/api/health`는 정상(postgresql HEALTHY, migrations APPLIED, fixtureMode false)이나 **DB가 비어 있어** 화면에 표시할 값이 없다.

### 4.5 아직 손대지 않은 것

- 로그인 게이트 완화는 **로컬 전용**이다. 운영 경로는 PD-006 그대로 두었다 (2.6 참고).
- 장중 근거 이력은 세션 안에서만 유지된다. 새로고침하면 사라진다. 다음 날 장 시작 전까지 진짜로 남기려면 서버가 이력을 내려줘야 한다.
- 검색(리서치) 화면은 자리만 있고 내용이 없다.
