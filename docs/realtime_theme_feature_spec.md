- 적용 범위: KRX 정규장 장중 홈의 실시간 테마 탐지·순위·상승 이유
- 관련 문서: [DAYJAVIEW PRD](./PRD.md), [화면 명세](./screen_spec.md), [제품 의사결정 기록](./product_decisions.md)

## 1. 한 줄 정의

DAYJAVIEW의 실시간 기능은 **키움의 시장 전체 후보 탐색 기능으로 움직이는 종목을 먼저 발견하고, 선택된 종목의 0B 주식체결 스트림을 받아 인포스탁 테마 기준 순위를 수초 단위로 갱신한 뒤, 자동 수집한 특징주 뉴스로 오늘 상승 이유를 확인하는 기능**이다.

여기서 실시간은 다음을 의미한다.

- 구독 중인 종목의 체결 수신과 내부 계산: 틱 발생 시 즉시
- 테마 지표와 순위 계산: 1초 이내 주기
- 사용자 홈 반영: 2~3초 이내
- 시장 전체 모든 종목의 모든 틱을 직접 받는 초저지연 전수 피드는 아님

따라서 사용자 표현은 **실시간**을 사용하되, 기술·운영 문서에서는 **수초 단위 준실시간**으로 정의한다.

## 2. 해결하려는 사용자 문제

사용자는 장중 홈에서 5초 안에 다음 질문에 답을 얻어야 한다.

1. 지금 어떤 테마가 가장 강한가?
2. 한 종목만 오르는가, 관련주가 함께 오르는가?
3. 현재 주도주는 누구인가?
4. 방금 순위가 급상승한 테마는 무엇인가?
5. 오늘 이 테마가 오르는 이유는 무엇인가?
6. 아직 이유가 확인되지 않았다면 어디까지 확인됐는가?
7. 장중 판단이 장후 인포스탁 분류와 달라졌는가?

## 3. 범위와 비범위

### 3.1 이번 기능에 포함

- 키움 실시간 조건검색을 이용한 시장 전체 후보 탐색
- 키움 0B 주식체결 WebSocket 구독
- 인포스탁 테마-종목 관계를 이용한 기존 테마 매핑
- 테마별 수익률·중앙값·확산도·거래 관심 계산
- 실시간 테마 순위와 급부상 배지
- 특징주 뉴스 자동 수집·저장과 뉴스 기반 상승 이유 확인
- 설명되지 않는 동반 상승 종목군 탐지
- 신규 테마의 임시 분류 또는 미분류 상태 표시
- 장중 Event ID 유지와 장후 인포스탁 동기화
- 홈 카드와 테마 상세의 수초 단위 갱신

### 3.2 이번 기능에서 제외

- 공시 수집과 DART 연동
- 텔레그램 주식방을 사용자 노출 근거로 사용하는 기능
- 키움이 제공하는 테마 분류를 DAYJAVIEW의 테마 기준으로 사용하는 기능
- KRX 전 종목의 모든 체결을 한 세션에서 전수 구독
- 거래소 직접 시세 수준의 밀리초 지연 보장
- 자동 매매와 종목 추천
- NXT·SOR 체결 통합

MVP는 KRX 정규장 기준으로 구현한다. NXT·SOR를 추가할 때는 동일 종목의 거래소별 코드를 하나의 canonical stock ID로 통합하고 기준 가격을 다시 정의해야 한다.

## 6. 데이터 소스와 역할

### 6.1 키움 REST API와 WebSocket

2026-08-13 공식 안내 기준으로 국내주식 조회 TR은 계좌별·토큰별 초당 5회, 세션당 실시간 시세는 200종목, 실시간 조건검색은 10건, 조건검색 결과 노출은 조건당 최대 100종목이다. 이 수치는 변경될 수 있으므로 배포 전 공식 안내를 다시 확인한다.

| 기능 | API | 방식 | DAYJAVIEW 용도 |
|---|---|---|---|
| 실시간 조건검색 | ka10173 | WebSocket | 시장 전체에서 조건 편입·이탈 종목 발견 |
| 주식체결 | 0B | WebSocket | 선택 종목의 체결·현재가·등락률·누적 거래대금 수신 |
| 업종지수 | 0J | WebSocket | KOSPI·KOSDAQ 시장 대비 초과수익률 기준 |
| 가격급등락 | ka10019 | HTTP 조회 | 최근 N분 급등 종목 안전망 |
| 거래량급증 | ka10023 | HTTP 조회 | 조건검색 누락 보완 |
| 전일대비등락률상위 | ka10027 | HTTP 조회 | 현재 강세 종목 안전망 |
| 거래대금상위 | ka10032 | HTTP 조회 | 유동성 있는 주도 종목 안전망 |
| 지정종목 정보 | ka10095 | HTTP 조회 | 여러 종목의 현재 스냅샷 보완 |

ka10095는 여러 종목코드를 | 문자로 구분해 요청할 수 있다. 실제 허용 길이와 안정적인 배치 크기는 PoC에서 측정해 결정한다.

ka00198 실시간종목조회순위는 투자자 조회 관심 성격의 순위이므로 등락률 순위나 테마 강도 계산에 사용하지 않는다. 0D 호가잔량도 이번 순위의 핵심 입력에서 제외한다.

중요한 점은 ka10173과 0B가 **REST API 서비스 안의 WebSocket 기능**이라는 것이다. HTTP로 1분마다 호출하는 구조가 아니다.

### 6.2 인포스탁

인포스탁은 DAYJAVIEW의 테마 taxonomy와 사후 확정 기준이다.

장 시작 전 사용하는 값:

- 테마
- 테마 동의어
- 테마-종목 관계
- 관련주 편입 이유
- 기존 테마 히스토리
- 직전 확인 버전

장후 갱신하는 값:

- 신규 테마
- 신규 히스토리 문장
- 당일 주도주
- 관련주 변경
- 편입 이유 변경

인포스탁 데이터의 API·파일·제휴 등 합법적인 사용 경로를 확보해야 한다. 화면 자동 수집을 전제로 구현하지 않는다.

### 6.3 뉴스

뉴스 수집은 테마 탐지와 독립된 백그라운드 파이프라인으로 운영한다. 사용자가 검색하거나 테마가 먼저 활성화돼야만 기사를 가져오는 구조로 만들지 않는다.

MVP 공급원 우선순위:

1. 사용 조건을 확인한 언론사의 경제·금융·증권 RSS
2. NAVER API HUB 뉴스 검색의 `특징주` 최신순 조회
3. 저장된 뉴스에서 근거를 찾지 못했을 때만 실행하는 종목명·테마명 보완 검색

RSS와 NAVER API HUB는 모두 외부에서 DAYJAVIEW로 기사를 직접 밀어주는 범용 push feed가 아니다. 서버 수집기가 장중 30~60초 간격으로 새 항목을 확인하고, 새 기사만 내부 이벤트 `feature_news.created`로 발행한다. 정확한 주기는 공급원 이용약관·호출 한도·실측 지연에 따라 조정한다.

수집 대상 초기 규칙:

- 제목에 `[특징주]`, `[특징주 강세]`, `[특징주 급등]` 등 특징주 표지가 있음
- 제목·요약에 상장 종목명이 식별됨
- 발행 시각이 전일 장 마감 이후이며 당일 판단 시점보다 미래가 아님
- 동일 원문 URL, 정규화 제목, 매체·발행 시각 조합이 기존 기사와 중복되지 않음

저장 항목:

- 원문 URL과 공급원 항목 ID
- 제목, 검색 API 또는 RSS가 제공한 요약·설명
- 발행 시각, 수집 시각, 매체
- 식별된 종목·기업·기술·정책 Entity
- 이용 범위와 처리 상태

기사 전문은 라이선스나 이용약관이 명시적으로 허용할 때만 처리·저장한다. 사용자 화면에는 기사 전문을 무단 재배포하지 않고 자체 요약, 매체, 발행 시각, 원문 링크를 제공한다.

테마가 CANDIDATE 또는 ACTIVE가 되면 먼저 특징주 뉴스 저장소에서 다음 키로 조회한다.

- 테마명과 동의어
- 현재 주도주와 상위 관련주
- 핵심 기업·기술·제품
- 정부·기관·국가·프로젝트명

저장된 기사로 설명되지 않을 때만 서버가 동일 키로 NAVER API HUB 보완 검색을 실행한다. 이 검색도 LLM이 수행하지 않으며, 결과는 같은 수집·중복 제거 절차를 거쳐 뉴스 저장소에 먼저 적재한다.

이번 MVP는 공시를 수집하지 않는다. 화면에서 이유를 찾지 못했을 때 공시가 없다는 뜻으로 해석해서도 안 된다.

### 6.4 기준정보

매일 장 시작 전에 다음 자료가 준비돼야 한다.

- 전일 조정종가
- 상장주식수
- 검증된 유동주식비율
- 최근 20거래일의 종목별 동일 시각 누적 거래대금
- 시장 구분
- 거래정지·관리·기업행위 플래그
- 테마별 Core·Related 역할

키움 0B에는 시가총액 필드가 있지만 유동주식비율은 제공하지 않는다. 유동주식비율은 KRX Open API와 OpenDART의 무료 공식 데이터를 조합해 산출하며, 실제 응답의 의미와 Coverage를 검증한 데이터만 사용한다. 유료·승인형 데이터상품은 사용하지 않는다.

자체 산출식은 `발행 보통주식수 - 중복 제거된 확인 가능 비유동 보통주식수`를 유동주식수로 정의한다. 비유동 지분에는 자기주식, 최대주주·특수관계인 보유분과 공식 공시에서 식별되는 보호예수·전략 보유분을 포함한다. 이 값은 KRX 유료 지수정보상품의 공식 유동비율이라고 표현하지 않는다.

모든 입력에는 `source`, 원문 식별자, `asOf`, `effectiveFrom`, 수집 시각과 산출 버전을 저장한다. 종목·주식 종류·보유자·기준일 기준으로 중복 차감을 방지하며, 기준일 충돌이나 해결하지 못한 중복이 있으면 해당 종목을 Coverage에서 제외한다.

검증된 유동주식비율을 확보하지 못한 경우 자기주식 제외 시가총액이나 총시가총액으로 대체하지 않는다. 영향을 받는 테마의 수익률은 계산 불가로 처리하며, 운영자 상태에는 누락 원인을 기록한다. 사용자 화면에서는 지표명을 바꾸지 않고 `데이터 갱신 중` 또는 `계산할 수 없음` 상태를 표시한다.

핵심은 **발견과 정밀 계산을 분리하는 것**이다.

- 조건검색은 전체 시장을 감시해 후보를 찾는다.
- 0B는 후보와 활성 테마 구성종목만 정밀 추적한다.
- 모든 테마를 매 틱 전수 계산하지 않고, 체결이 발생한 종목이 속한 테마만 증분 갱신한다.
- 뉴스 수집은 테마 탐지와 독립적으로 계속되고, 새 기사와 새 테마 양쪽 모두 로컬 매칭을 촉발한다.
- LLM은 외부 검색을 하지 않고 로컬 매처가 근거로 선택한 기사만 구조화한다.

## 8. 하루 운영 흐름

### 8.1 장 시작 전

1. 인포스탁 테마·종목 관계의 최신 버전을 적재한다.
2. 각 관계에 Core 또는 Related 역할을 부여한다.
3. 전일 조정종가·상장주식수·유동주식비율을 적재한다.
4. 종목별 유동시총과 테마 내 고정 가중치를 계산한다.
5. 최근 20거래일의 동일 시각 누적 거래대금 기준선을 준비한다.
6. 거래정지·기업행위·데이터 부족 종목을 표시한다.
7. 키움 인증·WebSocket 연결·조건식 버전을 점검한다.
8. 홈 초기 상태를 장 시작 대기로 배포한다.

### 8.2 장중

1. 뉴스 수집기가 RSS와 NAVER 특징주 최신순 결과를 30~60초마다 확인한다.
2. 새 기사만 중복 제거해 특징주 뉴스 저장소에 적재하고 `feature_news.created` 이벤트를 발행한다.
3. 실시간 조건검색이 종목의 조건 편입·이탈을 보낸다.
4. REST 안전망이 30~60초마다 조건검색 누락 후보를 보완한다.
5. 후보가 들어오면 인포스탁의 기존 테마를 역조회한다.
6. 후보와 해당 테마의 핵심 구성종목을 0B 구독 후보로 올린다.
7. 구독하지 못한 관련주는 ka10095로 최신 스냅샷을 보완한다.
8. 0B 틱이 들어올 때 해당 종목 상태와 연결 테마 지표만 갱신한다.
9. 활성화 조건을 충족한 테마를 활성 상태로 바꾸고 활성 테마끼리 백분위 순위 점수를 계산한다.
10. 테마 신규 활성화·주도주 변경·순위 급등 시 로컬 뉴스 저장소에서 관련 근거를 즉시 찾는다.
11. 새 특징주 기사가 들어오면 현재 CANDIDATE·ACTIVE 테마와 역방향으로 매칭한다.
12. 저장된 근거가 없을 때만 서버가 NAVER 보완 검색을 요청하고, 같은 검색어는 cooldown과 캐시를 적용한다.
13. 관련성이 기준을 통과한 기사에 한해 LLM이 종목·테마·상승 이유를 구조화하고 자체 요약을 만든다.
14. 홈에는 2~3초마다 시세·순위·상승 이유 변경분을 보낸다.
15. 중요한 상태 변화와 사용한 뉴스 근거를 Event State 로그로 저장한다.

### 8.3 장 마감 후

1. 활성 테마를 CLOSED로 전환하고 최종 장중 지표를 저장한다.
2. 같은 Event ID로 장중 기록을 보존한다.
3. 인포스탁 신규 업데이트를 수집한다.
4. 장중 임시 분류와 인포스탁 확정 분류를 매칭한다.
5. 기본 화면은 확정 분류를 사용한다.
6. 장중 이름 → 장후 이름 변경 이력을 보존한다.
7. 인포스탁과 매칭되지 않으면 `reconciliationStatus=UNMATCHED`, `reviewStatus=PENDING`으로 운영자 검수 대기한다.
8. 오탐·누락·주도주·상승 이유 일치율을 평가 데이터로 적재한다.

## 9. 시장 전체 후보 탐색

### 9.1 왜 모든 종목을 0B로 구독하지 않는가

테마를 완전히 전수 계산하려면 모든 종목의 최신 가격과 거래대금이 필요하다. 그러나 키움 공식 한도상 한 세션의 실시간 시세는 200종목이다.

따라서 DAYJAVIEW는 다음 2단계 구조를 사용한다.

~~~text
전체 시장
→ 조건검색·순위 조회로 넓게 발견
→ 발견된 후보와 관련 테마만 0B로 정밀 추적
~~~

이 구조는 움직임이 나타난 테마를 수초 단위로 찾는 데 적합하지만, 모든 비활성 테마의 정확한 틱별 순위를 보장하지는 않는다. 전 종목 완전 전수 순위가 제품 요구사항이 되면 키움 단일 세션이 아니라 정식 전 종목 시세 공급 계약을 검토해야 한다.

### 9.2 조건검색 구성 원칙

조건식은 영웅문4에서 만들고 API에서는 목록을 조회해 실행한다. 조건식 번호와 이름은 계정에 종속될 수 있으므로 운영 DB에서 버전 관리한다.

MVP 기본 종목군은 KOSPI·KOSDAQ 보통주다. ETF·ETN·ELW·스팩·우선주·정리매매·거래정지 종목은 기본 후보에서 제외한다. 신규 상장처럼 과거 기준선이 부족한 종목은 탐지 자체를 막지 않고 데이터 부족 플래그를 붙인다.

초기 조건식은 다음 신호를 나눠 포착한다.

| 후보군 | 목적 | 예시 기준 |
|---|---|---|
| 당일 강세 | 이미 시장 상위로 올라온 종목 | 일정 등락률 이상 + 최소 거래대금 |
| 단기 가속 | 방금 상승 속도가 붙은 종목 | 최근 N분 급등 |
| 거래량 급증 | 가격보다 거래가 먼저 붙는 종목 | 과거 대비 거래량 증가 |
| 거래대금 주도 | 실제 시장 영향이 큰 종목 | 당일 거래대금 상위 |
| 신고가·고가 근접 | 추세 강화 후보 | 당일 고가권 또는 신고가 |

조건검색 10개를 처음부터 모두 고정 사용하지 않는다. 초기 운영안은 8개를 사용하고 2개를 실험·장애 대응용으로 남긴다.

| 슬롯 | 조건식 역할 | 비고 |
|---|---|---|
| C01 | KOSPI 당일 강세 + 최소 거래대금 | 절대 강세 |
| C02 | KOSDAQ 당일 강세 + 최소 거래대금 | 절대 강세 |
| C03 | KOSPI 거래량 급증 | 거래 선행 신호 |
| C04 | KOSDAQ 거래량 급증 | 거래 선행 신호 |
| C05 | KOSPI 당일 고가 근접 | 추세 강화 |
| C06 | KOSDAQ 당일 고가 근접 | 추세 강화 |
| C07 | 전 시장 거래대금 주도 | 대형 주도주 보완 |
| C08 | 단기 가격 가속 | 영웅문4 지원 여부 PoC 확인 |
| C09 | 실험 슬롯 | 포화 조건 분리 등에 사용 |
| C10 | 예비 슬롯 | 장애·운영 대응 |

정확한 종목 임계값은 영웅문4 조건식에서 지원되는 항목과 실데이터를 확인한 뒤 확정한다. 조건 하나가 100종목에 도달하면 결과가 포화된 것으로 간주하고 다음 중 하나를 적용한다.

- KOSPI·KOSDAQ 분리
- 최소 거래대금 상향
- 등락률 구간 분리
- 조건검색 결과 포화 상태 기록
- REST 순위 조회와 합집합

### 9.3 REST 안전망

조건검색만으로 탐지 품질을 보장하지 않는다. 다음 조회를 30~60초마다 분산 호출한다.

- ka10019 가격급등락
- ka10023 거래량급증
- ka10027 전일대비등락률상위
- ka10032 거래대금상위

조회 호출은 토큰 버킷으로 초당 한도를 지키고, 장 시작 직후에는 모든 조회를 같은 초에 몰아 호출하지 않는다.

후보 종목 합집합에서 중복을 제거하고 다음 신호를 저장한다.

~~~text
stock_code
signal_type
signal_source
detected_at
condition_id
rank_at_detection
signal_value
~~~

## 10. 0B 실시간 체결 구독

### 10.1 0B가 하는 일

0B는 숫자 0 + 영문 B인 키움의 주식체결 실시간 타입이다. 등록한 종목에서 체결이 발생할 때마다 WebSocket으로 다음과 같은 값을 받는다.

- 체결시간
- 현재가
- 전일대비와 등락률
- 체결량
- 누적 거래량
- 누적 거래대금
- 시가·고가·저가
- 체결강도
- 순간 거래대금
- 시가총액

호가창 전체를 받는 기능이 아니며, 이번 테마 순위에는 0B만으로 충분하다.

### 10.2 구독 슬롯 정책

공식 상한 200종목을 꽉 채워 운영하지 않고 목표 구독 수를 180종목으로 둔다. 나머지 20개는 급격한 후보 유입과 등록 교체를 위한 여유다.

초기 목표 배분:

| 용도 | 목표 슬롯 |
|---|---:|
| 상위 활성 테마의 Core·주도 종목 | 120 |
| 신규 후보 종목 | 50 |
| 시장지수·리더·Coverage 보정 | 10 |
| 등록 교체 여유 | 20 |

실제 한도는 중복 제거된 종목 수 기준이다. 한 종목이 여러 테마에 속해도 슬롯은 하나만 사용한다.

우선순위:

1. 홈 상위 활성 테마의 현재 주도주
2. 홈 상위 활성 테마의 Core 종목
3. 방금 여러 탐지 신호에 동시에 포착된 후보
4. 활성 테마의 Related 종목
5. 단일 신호 후보

해제 원칙:

- 조건에서 이탈해도 즉시 해제하지 않고 초기 60초 cooldown을 둔다.
- 활성 테마에 속한 종목은 후보 신호가 사라져도 유지한다.
- 주도주와 Core 종목은 Related 종목보다 늦게 해제한다.
- 구독 변경은 1초 단위로 묶어 불필요한 churn을 줄인다.

60초 cooldown과 슬롯 배분은 초기 가설이며 부하 테스트 후 조정한다.

### 10.3 구독 외 종목 보완

활성 테마의 모든 관련주를 0B로 받을 수 없을 때 ka10095 스냅샷을 이용한다.

- 후보 테마가 처음 생겼을 때 구성종목 일괄 조회
- 활성 테마의 비구독 Related 종목 20~30초 보완
- 0B 재연결 직후 상태 복구
- Coverage 부족 시 우선 조회

스냅샷 데이터와 실시간 데이터는 source와 as_of를 따로 저장한다. 오래된 스냅샷을 방금 들어온 체결처럼 취급하지 않는다.

## 11. 종목 실시간 상태와 증분 계산

종목별 메모리 상태:

~~~text
stock_code
last_price
change_rate
cumulative_volume
cumulative_trading_value
open
high
low
last_trade_at
received_at
source                  REALTIME_0B | REST_SNAPSHOT
freshness
~~~

0B 틱 하나가 들어오면 전체 테마를 다시 계산하지 않는다.

~~~text
1. 종목의 이전 상태와 새 상태 차이 계산
2. stock_theme_index에서 연결된 테마 조회
3. 연결 테마의 합계·중앙값 입력·상승 종목 수 갱신
4. dirty_theme_set에 해당 테마만 추가
5. 다음 1초 계산 주기에 dirty theme만 재평가
~~~

이 방식이면 한 종목이 여러 테마에 속해도 연결된 테마만 갱신하면 된다.

## 12. 테마 활성화 상태

### 12.1 상태 모델

Event 장중 생명주기는 `lifecycleStatus`로 관리한다.

~~~mermaid
stateDiagram-v2
    [*] --> INACTIVE
    INACTIVE --> CANDIDATE: "후보 종목 탐지"
    CANDIDATE --> ACTIVE: "활성화 조건 지속 충족"
    CANDIDATE --> INACTIVE: "후보 신호 소멸"
    ACTIVE --> WEAKENING: "활성 기준 약화"
    WEAKENING --> ACTIVE: "10분 이내 재강화"
    WEAKENING --> CLOSED: "약화 지속 또는 장 마감"
~~~

장후 인포스탁 정합은 생명주기를 바꾸지 않고 `reconciliationStatus`로 별도 관리한다.

~~~mermaid
stateDiagram-v2
    [*] --> PENDING
    PENDING --> MATCHED: "자동 인포스탁 매칭 성공"
    PENDING --> UNMATCHED: "자동 매칭 실패"
    UNMATCHED --> MATCHED: "운영자 또는 후속 업데이트"
~~~

운영자 검수 진행 상태는 `reviewStatus=PENDING|RESOLVED`로 분리한다. 기존 초안의 `INFOSTOCK_MATCHED`와 `REVIEW_REQUIRED` 결합 상태는 각각 `MATCHED`, `UNMATCHED + reviewStatus=PENDING` 조합으로 대체한다. `AFTER_CLOSE_CONFIRMED`는 Event 생명주기가 아니라 상승 이유 근거 상태다. 상세 기준은 [system_architecture.md](./system_architecture.md)를 따른다.

사용자에게 내부 영문 상태는 노출하지 않는다.

### 12.2 초기 활성화 기준

다음 기준은 **백테스트 전 초기 가설**이다.

1. 최근 약 3분 안에 최소 2개 종목이 동반 강세 신호를 보임
2. 상한형 가중 테마 수익률이 +1.0% 이상
3. 테마 거래 관심 배수가 2.0배 이상
4. 종목별 거래 관심 배수가 2.0배 이상인 종목이 30% 이상이며 최소 2종목
5. 시장 대비 초과 수익률이 +0.5%p 이상
6. 위 조건이 10초 이상 유지

구성종목이 3개 미만인 테마는 데이터 부족으로 표시하고 일반 테마와 동일한 확산 신뢰도를 부여하지 않는다.

시장 대비 초과 수익률:

~~~text
테마 기준시장 수익률(t)
= Σ(종목 고정 가중치_i × 종목 소속시장 지수 수익률_i(t))

테마 초과 수익률(t)
= 테마 수익률(t) - 테마 기준시장 수익률(t)
~~~

KOSPI와 KOSDAQ 종목이 섞인 테마는 각 종목의 고정 가중치로 두 시장 지수를 혼합한다.

### 12.3 진입·이탈 흔들림 방지

- 활성화: 기준을 10초 유지해야 홈에 신규 진입
- 순위 교체: 새 순위가 5초 이상 유지되거나 점수 차가 큰 경우 즉시 반영
- 약화: 활성 기준 미달이 초기 60초 지속되면 WEAKENING
- 재강화: 같은 날·같은 촉매로 10분 이내 회복하면 같은 Event ID 유지
- 종료: 약화가 10분 지속되거나 장 마감 시 CLOSED

이 시간값 역시 실데이터로 조정한다. 핵심 원칙은 1~2틱 때문에 카드가 계속 나타났다 사라지지 않게 하는 것이다.

## 13. 실시간 테마 순위

### 13.1 순위 산식

같은 시각의 모든 활성 테마를 비교해 각 지표를 0~100 백분위로 변환한다.

~~~text
테마 순위 점수
= 40% × 상한형 유동시총 가중 테마 수익률 백분위
+ 25% × 구성종목 상승률 중앙값 백분위
+ 20% × 상승 종목 비율 백분위
+ 15% × 거래 관심 배수 백분위
~~~

내부 점수는 홈 정렬에만 사용하고 사용자에게 강도 92점처럼 노출하지 않는다.

### 13.2 상한형 유동시총 가중 테마 수익률

Core 종목만 사용한다.

~~~text
유동시가총액_i
= 전일 조정종가_i × 상장주식수_i × 유동주식비율_i

종목 등락률_i(t)
= 현재가_i(t) ÷ 전일 조정종가_i - 1

기본 가중치_i
= 유동시가총액_i ÷ Σ 유동시가총액

종목당 상한
= max(30%, 1 ÷ 유효 Core 종목 수)

테마 수익률(t)
= Σ(상한 적용 가중치_i × 종목 등락률_i(t))
~~~

상한 초과분은 아직 상한에 도달하지 않은 종목에 기존 비중대로 반복 재배분한다. 가중치는 전일 기준으로 장중 고정한다.

사용자 화면의 지표명은 항상 `테마 수익률`이다. 계산 기준 도움말에서만 `전일 기준 상한형 유동시가총액 가중`이라고 설명한다. 검증된 유동주식비율이 없으면 대체값으로 계산하지 않는다.

### 13.3 상승률 중앙값

Related를 포함한 유효 전체 구성종목의 당일 등락률 중앙값을 사용한다. 대형주 한 종목이 아니라 전형적인 관련주가 얼마나 움직였는지를 나타낸다.

### 13.4 상승 확산도

~~~text
상승 확산도(t)
= 등락률이 0% 초과인 유효 구성종목 수
  ÷ 유효 구성종목 수
~~~

화면에는 점수보다 다음처럼 표시한다.

~~~text
17 / 21종목 상승
~~~

### 13.5 거래 관심 배수

장중 현재 누적 거래대금은 과거 하루 전체 거래대금과 비교하지 않는다. 반드시 같은 시각끼리 비교한다.

~~~text
종목 기준 거래대금_i(t)
= 직전 20거래일의 t시각 누적 거래대금 중앙값_i

테마 거래 관심 배수(t)
= 현재 테마 구성종목의 t시각 누적 거래대금 합계
  ÷ 동일 구성종목의 종목별 기준 거래대금 합계
~~~

현재 테마 순위에는 최근 20거래일을 사용한다. 장기 관심 공백 계산은 제품 의사결정 PD-002에 따라 최근 60거래일 기준을 별도로 사용한다.

동일 시각 기준선을 만들려면 과거 장중 자료가 필요하다. 승인된 과거 분봉 데이터가 없으면 DAYJAVIEW가 매일 1분 단위 누적 거래대금 스냅샷을 직접 축적한다.

- 20거래일 이상: 정식 기준선 사용
- 5~19거래일: 가용 거래일 중앙값을 쓰되 PROVISIONAL 플래그 표시
- 5거래일 미만: 거래 관심 15% 항목을 전체 테마에서 일시 비활성화하고 나머지 85% 가중치를 같은 비율로 정규화

이 장중 과거 자료는 거래 관심 기준선에만 사용한다. 과거 유사 이벤트 검색이나 과거 성과 계산에 1분봉 패턴을 입력하는 것과는 별개다.

장 시작 직후에는 분모가 작아 값이 튈 수 있으므로 다음을 적용한다.

- 동일 시각 기준선을 1분 단위로 사전 계산
- 최소 과거 관측 수 미달 종목 제외
- 첫 수분의 극단값 winsorization 또는 상한 적용을 백테스트
- 데이터 부족 상태를 별도 기록

### 13.6 Coverage 기준

정확한 테마 순위로 인정하기 위한 초기 조건:

- Core 유동시총 비중의 80% 이상이 최신 상태
- Related 유효 종목 수의 70% 이상이 최근 상태
- 유효 Core 종목 최소 2개
- 유효 전체 종목 최소 3개

초기 freshness 기준:

- 0B: 해당 종목이 현재 등록 상태이고 WebSocket 세션 heartbeat가 정상
- 개별 종목의 마지막 체결 시각은 별도 표시하되, 거래가 없었다는 이유만으로 STALE 처리하지 않음
- REST 스냅샷: 수신 후 30초 이내
- 30초 초과: 낮은 신뢰도
- 60초 초과: 순위 제외 검토

Coverage가 부족하면 임의로 완전한 테마처럼 계산하지 않는다.

~~~text
데이터 갱신 중
~~~

으로 표시하고 홈 상위 노출을 제한한다.

### 13.7 겹치는 테마의 중복 부풀림 방지

한 종목이 여러 테마에 속할 수 있으므로 다음 보호 규칙을 적용한다.

- 종목당 가중치 최대 30%
- 활성화에 최소 2개 독립 동반 종목 요구
- 구성종목 겹침이 매우 높고 같은 뉴스 촉매이면 대표 테마와 하위 테마로 묶음
- 동일 대형주 하나만 움직인 여러 테마는 대형주 주도 상태로 표시
- 홈에서 거의 같은 구성의 카드가 연속 노출되지 않도록 canonical theme 우선

초기 중복 후보 기준은 종목 Jaccard overlap 0.8 이상으로 두되 백테스트로 확정한다.

### 13.8 현재 순위와 급부상 분리

홈의 기본 순위는 위 복합 점수로 정한다. 급부상은 별도 배지다.

급부상 후보:

- 최근 60초 순위 점수 증가
- 최근 5분 테마 수익률 증가
- 순위 상승 폭

즉 현재 1위와 방금 가장 빨라진 테마는 다를 수 있다.

## 14. 실시간 주도주

주도주는 단순 상승률 1위로 정하지 않는다. 기존 PRD의 Leader Score를 사용한다.

입력:

- 당일 등락률
- 테마 내 거래대금 순위
- 테마 대비 상대강도
- 현재가의 당일 고가 유지율
- 동반 관련주 수
- 뉴스의 직접 수혜 정도

홈에는 1개, 상세에는 상위 3~5개를 표시한다. 순위가 한두 틱마다 바뀌지 않도록 최소 유지시간을 둔다.

## 15. 오늘 오르는 이유 탐색

### 15.1 원칙

가격과 거래량은 **무엇이 움직이는지**를 먼저 알려주고, 뉴스는 **왜 움직이는지**를 나중에 확인한다.

특징주 기사는 주가 움직임 이후 작성되는 경우가 많으므로 최초 탐지 신호로 사용하지 않는다. 다만 기자가 확인한 원인과 시장 해석을 제공하므로 2차 확인 자료로는 유용하다.

상승 이유는 기사 내용을 그대로 차용하지 않는다. 관련 기사에서 확인 가능한 사건만 짧게 재서술하고 매체·발행 시각·원문 링크를 근거로 함께 제공한다.

### 15.2 수집과 매칭 실행 시점

수집과 매칭을 서로 분리한다.

#### A. 뉴스 수집 트리거

- 장중 RSS·NAVER `특징주` 최신순 수집: 30~60초 초기 주기
- 공급원에서 새 항목 발견: 즉시 중복 제거·저장
- 선택적 보완 검색 결과 도착: 동일 저장 파이프라인에 적재

수집기는 테마가 없을 때도 계속 동작한다. 따라서 특징주 기사가 테마보다 먼저 들어오면 저장해두었다가 나중에 활성화된 테마와 연결할 수 있다.

#### B. 로컬 뉴스 매칭 트리거

- 테마가 CANDIDATE 또는 ACTIVE가 됨
- 주도주가 변경됨
- 순위가 3계단 이상 상승
- 미분류 동반 상승 종목군이 생성됨
- 새 특징주 기사가 뉴스 저장소에 들어옴

앞의 네 이벤트는 `테마 → 최근 뉴스` 조회를, 마지막 이벤트는 `새 기사 → 현재 테마` 역방향 조회를 실행한다. 로컬 DB 조회는 외부 API 재검색이 아니므로 이벤트가 발생할 때 즉시 수행한다.

#### C. 선택적 보완 검색 트리거

다음 조건을 모두 만족할 때만 서버가 NAVER API HUB에 종목명·테마명 보완 검색을 요청한다.

1. CANDIDATE 또는 ACTIVE 테마에 로컬 뉴스 근거가 없음
2. 마지막 동일 검색 이후 cooldown이 지남
3. 외부 API 한도와 우선순위 큐에 여유가 있음

보완 검색은 LLM이 하지 않는다. 서버가 고정된 검색어 생성 규칙으로 API를 호출하고 결과를 뉴스 저장소에 적재한 뒤 로컬 매칭을 다시 실행한다.

### 15.3 뉴스 후보 점수와 매칭 범위

각 뉴스에 다음 항목을 평가한다.

- 테마명·동의어와의 의미적 관련성
- 주도주와의 직접 관련성
- 기사 시각과 가격 반응 시각의 근접성
- 여러 관련주를 동시에 설명하는 정도
- 같은 사건을 다루는 독립 매체 수
- 원문 출처의 명확성
- 기존 Event Ontology와의 연결성

기사 제목에 특징주가 포함됐다는 이유만으로 높은 점수를 주지 않는다.

시간 범위 초기안:

1. 테마 활성화 직전 60분
2. 당일 장 시작 이후
3. 전일 장 마감 이후의 미리 알려진 사건

판단 시점보다 나중에 발행된 기사를 과거 상태의 근거로 소급 적용하지 않는다. 새 기사가 들어와 상승 이유가 갱신되면 `evidence_confirmed_at`을 별도로 기록한다.

### 15.4 LLM 사용 범위

LLM은 뉴스 수집이나 인터넷 검색에 사용하지 않는다. 규칙 기반 종목명 매칭과 뉴스 후보 점수를 통과한 기사에만 호출한다.

LLM 입력:

- 선택된 기사의 제목·요약과 이용이 허용된 본문 일부
- 기사 원문 URL·매체·발행 시각
- 매칭 후보 종목과 현재 테마
- 가격 반응 시작 시각

LLM 출력:

~~~json
{
  "stockIds": ["stock_001"],
  "candidateThemeIds": ["theme_abc"],
  "catalystSummary": "비만치료제 기술수출 기대감 관련 보도",
  "eventEntities": ["비만치료제", "기술수출"],
  "confidence": 0.91,
  "grounded": true
}
~~~

금지 사항:

- LLM이 웹을 직접 검색하거나 URL을 새로 선택함
- 기사에 없는 원인을 일반 금융 지식으로 보충함
- 관련 기사가 없는데 상승 이유를 생성함
- 한 기사에서 확인한 내용을 복수 매체 확인으로 표현함
- 기사 문장을 길게 복제하거나 기사 전문을 사용자에게 재배포함

규칙만으로 종목·테마·원인을 충분히 구조화할 수 있으면 LLM을 호출하지 않아도 된다. 모델명, 프롬프트 버전, 입력 기사 ID, 출력 신뢰도를 저장해 결과를 재현할 수 있어야 한다.

### 15.5 상태와 사용자 문구

| 내부 상태 | 화면 문구 |
|---|---|
| SEARCHING | 상승 이유 확인 중 |
| SINGLE_SOURCE | 뉴스 기반 추정 |
| MULTI_SOURCE_CONFIRMED | 복수 뉴스 확인 |
| NO_NEW_CATALYST | 확인된 신규 소재 없음 |
| REEMERGENCE | 기존 소재 재부각 |
| AFTER_CLOSE_CONFIRMED | 인포스탁 기준 확정 |

확실하지 않은 이유를 확정 문장으로 쓰지 않는다.

좋은 예:

~~~text
상승 이유 확인 중
~~~

~~~text
AI 데이터센터 전력 투자 확대 관련 보도
뉴스 기반 추정 · 10:18
~~~

나쁜 예:

~~~text
AI 전력 투자 확대로 상승
~~~

근거가 충분해지기 전에는 인과를 단정하지 않는다.

### 15.6 텔레그램 정책

텔레그램 주식방은 다음 이유로 MVP의 공식 뉴스 공급원에서 제외한다.

- 출처와 원문이 불명확할 수 있음
- 삭제·수정 이력 추적이 어려움
- 재배포 권리와 서비스 약관 문제가 있음
- 루머가 사실처럼 섞일 수 있음

향후 사용하더라도 운영자용 빠른 제보 신호로만 받고, 반드시 언론 원문이나 공식 출처로 교차 확인한 뒤 사용자에게 노출한다.

## 16. 신규 테마 발생 흐름

### 16.1 탐지 조건

기존 인포스탁 테마 하나로 충분히 설명되지 않는 종목군에서 다음을 본다.

1. 3~5분 안에 최소 3종목 동반 상승
2. 종목별·군집별 거래대금 증가
3. 기존 테마와의 구성종목 overlap이 낮음
4. 공통 회사·기술·정책·산업 Entity 존재
5. 공통 뉴스가 있거나 뉴스 확인 중 상태

신규 테마는 한 종목만으로 생성하지 않는다.

### 16.2 처리 흐름

~~~mermaid
flowchart TD
    A["설명되지 않는 후보 종목 3개 이상"] --> B["3~5분 동반 움직임·거래대금 확인"]
    B --> C{"기존 인포스탁 테마로 설명 가능한가?"}
    C -->|예| D["기존 테마 활성화"]
    C -->|아니오| E["미분류 동반 상승 Event 생성"]
    E --> F["저장된 특징주 뉴스·Entity 로컬 매칭"]
    F --> G{"공통 근거가 충분한가?"}
    G -->|아니오| H["상승 이유 확인 중으로 유지"]
    G -->|예| I["임시 테마명 생성·신규 배지"]
    H --> M["조건 충족 시 서버 보완 검색"]
    M --> F
    I --> J["운영자 검수"]
    J --> K["장후 인포스탁 업데이트와 매칭"]
    K --> L["병합·하위테마·별도 유지"]
~~~

### 16.3 이름을 모를 때

공통 뉴스가 없으면 억지로 이름을 만들지 않는다.

~~~text
미분류 동반 상승
관련주 4개
상승 이유 확인 중
~~~

공통 뉴스와 Entity가 충분하면 임시 이름을 붙인다.

~~~text
우주 데이터센터               신규·임시
궤도형 데이터센터 프로젝트 관련 보도
관련주 5개
~~~

### 16.4 장후 인포스탁과 다를 때

예:

~~~text
장중 임시 분류     AI 전력인프라
장후 인포스탁      전력설비
~~~

기본 화면은 장후 확정값을 사용한다. 그러나 같은 Event ID를 유지하고 다음 이력을 저장한다.

~~~text
classification_version
source                  LIVE_ENGINE | OPERATOR | INFOSTOCK
old_theme_id
new_theme_id
changed_at
reason
~~~

사용자는 상세 이력에서 장중 분류와 장후 분류를 확인할 수 있다. 분류가 바뀌었다고 장중 기록을 삭제하지 않는다.

## 21. 장애와 저하 모드

### 21.1 0B 연결 끊김

1. WebSocket heartbeat·PING/PONG·등록 상태와 마지막 정상 메시지 시각을 추적한다.
2. 개별 종목에 새 체결이 없는 상태와 세션 장애를 구분한다.
3. heartbeat 실패 또는 연결 종료 시 전체 실시간 상태를 DEGRADED로 전환한다.
4. 자동 재연결과 재구독을 수행한다.
5. ka10095로 상태를 복원한다.
6. 목표 복구시간을 넘겨 전체 실시간 수신이 중단되면 홈에 지연 안내를 표시한다.

### 21.2 조건검색 결과 포화

- 조건별 결과 100개 도달을 작업 상태와 기본 로그에 기록
- 시장별·신호별 조건 분리
- 최소 거래대금 상향
- REST 순위 합집합으로 보완
- 포화 시간대의 장후 누락률 별도 측정

### 21.3 200종목 슬롯 부족

- 저우선 후보부터 해제
- 홈 상위 활성 테마의 Core·주도주 유지
- Related 종목은 REST 스냅샷으로 전환
- Coverage 미달 테마는 데이터 갱신 중 표시

### 21.4 뉴스 수집 실패 또는 근거가 없음

- RSS 한 곳이 실패하면 다른 RSS와 NAVER 수집은 계속 운영
- NAVER API가 실패하면 저장된 뉴스 DB의 로컬 매칭은 계속 운영
- 마지막 정상 수집 시각과 공급원별 지연 상태를 운영 화면에 표시
- 수집 지연과 실제로 관련 기사가 없는 상태를 내부적으로 구분
- 근거가 없으면 LLM을 호출하지 않고 이유를 생성하지 않음
- 상승 이유 확인 중을 유지하고, 일정 시간 후 확인된 신규 소재 없음 또는 기존 소재 재부각으로 분류
- 장후 인포스탁 업데이트가 오면 같은 Event ID에 반영

### 21.5 인포스탁 업데이트 지연

- 장중 분류를 미확정 상태로 유지
- 동기화를 재시도
- 과거 화면을 임의로 덮어쓰지 않음
- 최종 동기화 시 분류 변경 이력 저장

### 21.6 유동시총 자료 없음

- 대체 시총으로 계산
- weight_method와 데이터 버전 저장
- 사용자 문구에서 유동시총이라는 표현을 사용하지 않음

### 21.7 기업행위·거래정지

- 권리락·분할 미반영 종가는 계산에서 제외
- 거래정지 종목은 확산도 분모 정책을 별도 플래그로 기록
- 급격한 가격 변화가 기업행위 때문이면 오탐 분석 대상에 포함

## 22. 성능·품질 목표

### 22.1 실시간 성능

- 0B 수신 → 서버 종목 상태 반영 P95 500ms 이내
- 0B 수신 → dirty 테마 재계산 P95 1초 이내
- 0B 수신 → 사용자 홈 반영 P95 3초 이내

- 주도주 일치율

### 22.3 상승 이유 품질

- 장후 인포스탁 상승 사유와 장중 뉴스 요약의 일치율

- 뉴스-테마 매칭 정밀도와 재현율
- LLM 출력의 기사 근거 충실도
- 로컬 뉴스로 해결되지 않아 외부 보완 검색을 실행한 비율
- 이유 최초 확인까지 걸린 시간
- 운영자 수정률
- 잘못된 원인 연결률
- 이유 미확인 상태를 잘못 확정하지 않은 비율

### 22.4 데이터 품질

- 상위 카드 Core Coverage 80% 이상
- 최신 시세 timestamp 누락률
- 유동시총 대체값 사용 비율
- WebSocket 재연결 후 상태 복구 시간
- Event ID 중복·유실 건수

## 23. 백테스트와 검증 항목

출시 전 다음 값을 비교한다.

- 종목당 시총 상한 20%·25%·30%·35%
- 활성화 테마 수익률 +0.5%·+1.0%·+1.5%
- 거래 관심 배수 1.5·2.0·2.5배
- 거래 관심 확산도 20%·30%·40%
- 시장 초과수익률 +0.3%p·+0.5%p·+1.0%p
- 활성화 지속시간 5·10·20초
- 약화 판정 30·60·120초
- Coverage 기준 70%·80%·90%
- 순위 가중치 조합
- 조건검색 조합별 장후 재현율
- 신규 테마 최소 종목 수 3·4·5개
- 테마 overlap 병합 기준 0.7·0.8·0.9

검증 데이터는 장중 Event State 로그와 장후 인포스탁 결과를 같은 Event ID로 연결해 만든다. 과거 1분봉을 실시간 처리의 원본처럼 재현하지는 않되, 임계값 백테스트용 보조 데이터로 사용하는 것은 별도 실험 설계에서 결정한다.

## 25. MVP 완료 조건

다음 조건이 모두 충족되면 실시간 테마 MVP를 완료로 본다.

1. 조건검색으로 전체 시장 후보를 받고 0B 후보 구독으로 자동 전환된다.
2. 기존 인포스탁 테마 최소 1개가 실제 장중 체결에 따라 활성화된다.
3. 홈 순위가 2~3초 주기로 갱신된다.
4. 순위 산식의 네 입력과 Coverage를 운영 화면에서 검증할 수 있다.
5. 200종목을 넘을 때 우선순위 해제와 REST 보완이 동작한다.
6. 특징주 뉴스가 사용자 검색 없이 자동 수집되고 중복 저장되지 않는다.
7. 테마 상태 변화와 새 기사 도착 양쪽에서 로컬 매칭이 실행된다.
8. LLM이 외부 검색 없이 선택된 기사만 구조화하며, 뉴스가 없을 때 이유를 만들어내지 않는다.
9. 사용한 상승 이유에 기사 ID·매체·발행 시각·원문 링크가 연결된다.
10. 장중 이벤트와 장후 인포스탁 분류가 같은 Event ID로 연결된다.
11. WebSocket 재연결 뒤 상태가 복구된다.
12. 모든 홈 카드에 마지막 갱신 시각과 데이터 상태가 존재한다.
13. 백테스트 전 가설값과 확정값이 설정 파일·문서에서 구분된다.

## 26. 현실적인 한계와 제품 표현

가능한 것:

- 시장 전체 조건검색 기반 후보 발견
- 선택 종목의 체결 단위 실시간 추적
- 활성 테마의 수초 단위 순위
- 수집기가 새 특징주 기사를 확인한 뒤 상승 이유 보완
- 인포스탁 기준의 장중 분류와 장후 확정

보장할 수 없는 것:

- 모든 KRX 종목의 모든 체결을 키움 한 세션으로 전수 수신
- 신규 테마 이름을 가격만으로 즉시 정확하게 생성
- 주가 움직임보다 항상 먼저 상승 이유 확인
- 모든 언론사의 특징주 기사를 누락 없이 즉시 수신
- 특징주 기사만으로 최초 움직임 포착
- 인포스탁 장후 결과와 장중 분류의 100% 일치

따라서 외부 표현은 다음이 적절하다.

> 시장 전체에서 강해지는 종목을 감지하고, 활성 테마를 수초 단위로 갱신합니다.

다음 표현은 사용하지 않는다.

> 전 종목 모든 체결을 완전 실시간으로 분석합니다.
