## PD-001. 현재 테마 수익률에 상한형 유동시가총액 가중 적용

- 결정일: 2026-08-13
- 상태: 채택
- 적용 대상: 장중 및 장후의 **현재 테마 반응**과 홈의 테마 정렬
- 적용 제외: 테마 확산도, 과거 유사 이벤트 성과, 개별 종목 수익률

### 배경

구성종목의 등락률을 단순평균 또는 중앙값만으로 집계하면 시가총액이 큰 종목의 의미 있는 움직임이 과소평가될 수 있다.

예를 들어 시가총액이 큰 핵심 종목이 4% 상승하고 다수의 소형 관련주가 보합이면, 단순평균에서는 해당 테마가 상위에 잡히지 않을 수 있다. 반대로 순수 시가총액 가중만 사용하면 대형주 한 종목이 여러 관련 테마의 순위를 동시에 지배할 수 있다.

따라서 DAYJAVIEW는 다음 두 관점을 분리해서 사용한다.

```text
상한형 유동시총 가중 수익률 = 테마가 시장가치에 미친 영향
상승 종목 수 / 전체 종목 수 = 테마 내부의 확산 정도
```

시가총액 변화는 시장가치의 재평가이며, 동일 금액의 현금이 순유입됐다는 뜻으로 해석하지 않는다.

### 결정

1. 현재 테마 수익률은 **상한형 유동시가총액 가중 수익률**로 계산한다.
2. 총시가총액이 아니라 실제 거래 가능한 지분을 반영한 **유동시가총액**을 사용한다.
3. 가중치는 장중 현재가가 아니라 **전일 종가 기준으로 고정**한다.
4. 대형주 한 종목의 과도한 지배를 막기 위해 종목당 가중치 상한을 둔다.
5. 초기 상한은 30%로 설정하되, 정식 확정 전 20%·25%·30%·35%를 백테스트한다.
6. 시총 가중 수익률을 단독 순위 기준으로 사용하지 않고 확산도·중앙값·거래대금 증가율과 결합한다.
7. 유동시총 가중 계산에는 해당 테마의 직접 수혜·핵심 구성종목만 사용한다. 전체 관련주는 확산도 계산에 사용한다.
8. 사용자 화면의 지표명은 화면과 데이터 상태에 관계없이 **`테마 수익률`**로 고정한다.
9. `가중 수익률`, `대형주 반영 테마 수익률`, `시총 상한 가중 수익률` 같은 계산 방식 명칭은 사용자 화면의 지표명으로 사용하지 않는다. 계산 기준 도움말에서만 **`전일 기준 상한형 유동시가총액 가중`**이라고 설명한다.
10. 검증된 유동주식비율을 확보하지 못한 경우 총시가총액이나 자기주식 제외 시가총액으로 조용히 대체하지 않는다. 해당 테마 수익률을 계산 불가 상태로 처리하고 출시 게이트를 통과시키지 않는다.

### 계산식

#### 1. 종목별 유동시가총액

```text
유동시가총액_i
= 전일 종가_i × 상장주식수_i × 유동주식비율_i
```

- 전일 종가는 권리락, 액면분할 등 기업행위를 반영한 조정값을 사용한다.
- 유동주식비율 데이터가 갱신되면 적용일과 버전을 저장한다.

#### 2. 종목별 당일 등락률

```text
종목 등락률_i(t)
= 현재가_i(t) ÷ 전일 조정종가_i - 1
```

장후에는 현재가 대신 당일 조정종가를 사용한다.

#### 3. 기본 가중치

```text
기본 가중치_i
= 유동시가총액_i ÷ Σ 유동시가총액
```

#### 4. 가중치 상한

```text
종목당 가중치 상한
= max(30%, 1 ÷ 유효 구성종목 수)
```

- 상한을 초과한 비중은 상한에 도달하지 않은 종목에 기존 비중대로 재배분한다.
- 모든 종목이 상한 이하가 될 때까지 재배분을 반복한다.
- `1 ÷ 유효 구성종목 수`를 함께 사용하는 이유는 구성종목이 2~3개인 신규 테마에서도 합계 100%가 가능한 상한을 만들기 위해서다.

#### 5. 테마 수익률

```text
테마 수익률(t)
= Σ(상한 적용 가중치_i × 종목 등락률_i(t))
```

### 홈 테마 정렬

테마 수익률은 홈 순위의 한 요소로만 사용한다. 초기 내부 계산식은 다음과 같다.

```text
테마 순위 점수
= 40% × 테마 수익률 백분위
+ 25% × 구성종목 상승률 중앙값 백분위
+ 20% × 상승 종목 비율 백분위
+ 15% × 거래대금 증가율 백분위
```

- 각 백분위는 같은 시각의 전체 활성 테마를 비교해 0~100으로 환산한다.
- 테마 순위 점수 자체는 사용자에게 노출하지 않고 홈 정렬에만 사용한다.
- 위 가중치는 초기값이며 탐지 누락률과 장후 주요 테마 일치율을 이용해 조정한다.

거래대금 증가율은 다음과 같이 계산한다.

```text
종목 기준 거래대금_i(t)
= 직전 20거래일의 t시각 누적 거래대금 중앙값_i

테마 거래대금 증가율(t)
= 테마 구성종목의 t시각 누적 거래대금 합계
  ÷ 동일 구성종목의 종목별 기준 거래대금 합계
```

- 장중에는 반드시 같은 시각까지의 누적 거래대금을 비교한다. 오전 누적값을 과거 하루 전체 거래대금과 비교하지 않는다.
- 장 마감 후에는 각 거래일의 하루 전체 거래대금을 사용한다.
- 현재 순위 계산은 직전 20거래일을 사용하고, 장기 관심 공백 계산은 PD-002의 직전 60거래일 기준을 별도로 사용한다.

### 화면 적용

| 화면 또는 숫자 | 적용 | 기준 |
|---|---:|---|
| 홈 테마 정렬 | 적용 | 복합 테마 순위 점수의 40% 입력값 |
| 홈 카드의 `테마 수익률` | 선택 적용 | 사용자 지표명은 항상 `테마 수익률` |
| 이벤트 상세의 `테마 수익률` | 적용 | 사용자 지표명은 항상 `테마 수익률` |
| 이벤트 상세의 시장 테마 순위 | 간접 적용 | 복합 테마 순위 점수로 산출 |
| `17 / 21종목 상승` | 미적용 | 종목 수를 동일하게 1개씩 집계 |
| 주도주 선정 | 미적용 | 등락률·거래대금·고가 유지율 등으로 별도 판단 |
| 과거 T+1·T+5·T+20 | 미적용 | 당시 주도주 동일가중 바스켓 유지 |
| 과거 MFE·MAE | 미적용 | 당시 주도주 바스켓 기준 유지 |
| 개별 종목 수익률 | 미적용 | 해당 종목의 실제 수익률 표시 |

### 사용자 화면 표현

홈에서는 수치 자체보다 정렬과 상태 분류에 우선 사용한다. 필요한 경우 다음처럼 표현한다.

```text
방산                              대형주 주도

한화에어로스페이스                     +4.0%
24종목 중 7종목 상승
```

이벤트 상세에서는 시장 영향과 확산도를 함께 보여준다.

```text
지금 움직임

테마 수익률                             +2.7%
함께 오른 종목                          7 / 24
주도주                  한화에어로스페이스 +4.0%

계산 기준: 전일 기준 상한형 유동시가총액 가중
```

`테마 수익률`은 단독으로 보여주지 않고 반드시 `함께 오른 종목`과 함께 보여준다.

### 상태 표현 규칙

한 종목의 기여가 크지만 확산도가 낮은 경우:

```text
대형주 주도
```

다수 종목으로 상승이 확산된 경우:

```text
테마 전반 확산
```

상태 분류의 정확한 임계값은 실제 데이터 백테스트 후 별도 결정으로 기록한다.

### 과거 유사 이벤트 성과에 적용하지 않는 이유

과거 유사사례 통계의 목적은 시장 전체 가치의 변화를 측정하는 것이 아니라, 각 사건 당시 주도주를 매매했을 때의 전형적인 이후 결과를 비교하는 것이다.

따라서 다음 원칙을 유지한다.

```text
과거 이벤트 당시 주도주
→ 주도주 동일가중 바스켓 수익률
→ 이벤트 하나당 하나의 관측값
→ 유사 이벤트 수익률의 중앙값
```

과거 성과까지 시총 가중하면 대형주가 포함된 일부 사건이 통계를 지배하고, 시대별 시가총액 차이로 인해 사건 간 비교가 왜곡될 수 있다.

### 검증 과제

- 종목당 상한 20%·25%·30%·35% 비교
- 순수 시총 가중, 상한형 시총 가중, 제곱근 시총 가중 비교
- 대형주 단독 상승 테마의 과대평가 여부
- 주요 테마 탐지 누락률
- 장후 인포스탁 주요 테마와 홈 상위 테마의 일치율
- 한 종목이 여러 테마에 속할 때 순위가 동시에 부풀려지는 정도
- 핵심 구성종목 분류 오류가 순위에 미치는 영향

## PD-002. 장기 미관심 상태는 가격 위치가 아니라 `관심 공백`으로 표시

- 상태: 초기 제품 결정, 임계값은 백테스트 전 가설
- 결정일: 2026-08-13
- 적용 대상: 활성 테마 홈 배지, 테마 상세 요약, 전체 테마 목록
- 적용 제외: 테마 수익률, 과거 유사사례 수익률, 홈 순위 점수

### 사용자 질문

이 값이 답해야 하는 질문은 다음과 같다.

> 이 테마가 오랜 기간 시장의 관심을 받지 못하다가 다시 움직이는가?

52주 또는 3년 고점·저점 사이의 현재 가격 위치만으로는 이 질문에 답할 수 없다. 최근 급락한 인기 테마도 가격 위치가 낮아질 수 있고, 오랫동안 거래 없이 횡보한 테마는 가격 범위의 중간에 있을 수 있다.

따라서 `소외지수`라는 합성 점수는 사용하지 않는다. 화면에서는 `마지막 주목`, `관심 공백`, `N개월 만에 재점화`처럼 의미가 직접 드러나는 값을 사용한다.

### 1. 종목별 거래 관심 배수

시각 `τ`까지의 종목별 누적 거래대금을 같은 시각의 과거 값과 비교한다.

```text
종목 거래 관심 배수(i, t, τ)
= t일 τ시각까지의 누적 거래대금(i)
  ÷ 직전 60거래일의 τ시각 누적 거래대금 중앙값(i)
```

- 장 마감 후에는 각 거래일의 하루 전체 거래대금을 사용한다.
- 장중에는 반드시 동일 시각까지의 누적 거래대금을 비교한다. 오전 누적값을 과거 하루 전체 거래대금과 비교하지 않는다.
- 해당 날짜 당시의 테마 구성종목을 사용한다. 현재 구성종목을 과거 전체 기간에 소급 적용하지 않는다.
- 거래정지 종목과 비교 가능한 과거 관측값이 40개 미만인 종목은 그날 계산에서 제외한다.

### 2. 테마 거래 관심 배수와 확산

```text
테마 거래 관심 배수(t, τ)
= 유효 구성종목의 현재 누적 거래대금 합계
  ÷ 유효 구성종목별 직전 60거래일 동일 시각 거래대금 중앙값의 합계
```

```text
거래 관심 확산도(t, τ)
= 종목 거래 관심 배수가 2배 이상인 구성종목 수
  ÷ 유효 구성종목 수
```

합산 거래대금은 실제로 유입된 자금 규모를 반영하고, 확산도는 대형주 한 종목만으로 테마가 재점화된 것처럼 보이는 오류를 막는다.

### 3. 테마 주목일

초기 규칙은 다음 세 조건을 모두 만족한 거래일이다.

1. 테마 거래 관심 배수 `2.0배 이상`
2. 종목 거래 관심 배수가 2배 이상인 종목이 유효 구성종목의 `30% 이상`이며 최소 `2종목 이상`
3. 해당 시점의 상한형 유동시가총액 가중 테마 수익률 `+1.0% 이상`

유효 구성종목이 3개 미만이면 `관심 공백`을 계산하지 않고 `데이터 부족`으로 처리한다.

`2.0배`, `30%`, `+1.0%`는 제품 출시 전 백테스트로 확정할 초기값이다. 확정 전 사용자 화면에는 실험값임을 표시하고, 확정 후 변경 이력을 이 문서에 남긴다.

### 4. 관심 구간과 관심 공백

하나의 상승 파동이 여러 날 이어져도 매일 새로 재점화된 것으로 계산하지 않는다.

- 첫 테마 주목일에 관심 구간이 시작된다.
- 이후 테마 주목일이 다시 나타나면 같은 관심 구간으로 본다.
- 테마 주목일이 10거래일 연속 나타나지 않으면 구간이 종료된 것으로 확정한다.
- 구간 종료일은 마지막 테마 주목일이다.

현재 관심 구간이 시작됐을 때의 관심 공백은 다음과 같다.

```text
관심 공백 거래일 수
= 직전 관심 구간의 마지막 주목일과
  현재 관심 구간의 첫 주목일 사이에 존재하는 KRX 거래일 수
```

현재 관심 구간이 이어지는 동안에는 같은 관심 공백 값을 유지한다. 오늘도 주목 조건을 만족한다고 `0일`로 다시 계산하지 않는다.

### 5. 화면 표현

#### 오늘 홈

관심 공백이 60거래일 이상인 활성 테마에만 기존 `재점화` 배지를 다음처럼 교체한다.

```text
원전수출                    8개월 만에 재점화
```

- 별도 숫자 행을 추가하지 않는다.
- 표시 개월 수는 `관심 공백 거래일 수 ÷ 21`을 반올림한다.
- 60거래일 미만이면 배지를 표시하지 않는다.

#### 테마 상세 요약

현재 소재와 소재 상태 바로 아래에 한 문장으로 먼저 보여준다.

```text
8개월 만에 다시 주목받고 있어요
```

`현재 반응`과 `발생 전` 영역에 근거를 나눠 보여준다.

```text
현재 반응
오늘 거래 관심          평소 대비 2.4배

발생 전
이전 주목               2025.12.03
관심 공백               163거래일
```

`평소 대비 2.4배`는 위의 `테마 거래 관심 배수`이며, 직전 60거래일 동일 시각 중앙값을 기준으로 한다.

#### 전체 테마 목록

- 현재 활성 테마: `8개월 만에 재점화`
- 비활성 테마: `마지막 주목 5개월 전`
- 기존의 `히스토리 24건`은 목록에서 제거하고 상세 히스토리로 이동한다.

### 6. 가격 위치와의 관계

52주 가격 위치를 제공하더라도 `관심 공백`과 합치지 않는다. 필요한 경우 테마 상세의 접힌 보조 정보에서 `최근 1년 가격 위치`로만 제공한다.

```text
최근 1년 가격 위치
= 100 × (현재값 - 최근 1년 최저값)
  ÷ (최근 1년 최고값 - 최근 1년 최저값)
```

가격 위치는 현재 가격 수준을 설명하고, 관심 공백은 시장의 거래 관심이 없었던 기간을 설명한다.

### 검증 과제

- 거래 관심 배수 기준 1.5·2.0·2.5배 비교
- 확산도 기준 20%·30%·40% 비교
- 상승률 기준 0%·1%·2% 비교
- 관심 구간 종료 기준 5·10·15거래일 비교
- 인포스탁의 실제 테마 부각일 재현율과 오탐률
- 대형주 한 종목만 거래가 집중된 날의 오탐률
- 장중 판정과 장후 확정 판정의 일치율

## PD-003. 특징주 뉴스는 상시 자동 수집하고 LLM은 매칭된 근거만 구조화

- 상태: 채택
- 결정일: 2026-08-13
- 적용 대상: 장중 실시간 테마의 상승 이유, 신규 테마 임시 명명, 뉴스 근거 표시
- 적용 제외: 가격·거래량 기반 최초 테마 탐지, 테마 순위 계산, 공시 수집

### 배경

테마가 움직일 때마다 LLM이 인터넷을 검색하게 하면 외부 검색 결과와 모델 동작에 따라 지연·비용·재현성이 달라지고, 근거가 없을 때 모델이 그럴듯한 원인을 보충할 위험이 있다.

반대로 특징주 기사만 기다렸다가 테마를 탐지하면 기사 작성 시점만큼 최초 감지가 늦어진다. 따라서 가격·거래량 탐지와 뉴스 수집을 독립적으로 운영하고, 둘이 만나는 시점에만 상승 이유를 확인한다.

### 결정

1. 가격·거래량 엔진이 무엇이 움직이는지 먼저 탐지한다.
2. 특징주 뉴스 수집기는 테마 상태와 관계없이 장중 계속 동작한다.
3. 1차 공급원은 이용 조건을 확인한 언론사 RSS, 보완 공급원은 NAVER API HUB의 `특징주` 최신순 조회로 한다.
4. 새 기사는 원문 URL·정규화 제목·매체·발행 시각으로 중복 제거한 뒤 내부 뉴스 저장소에 적재한다.
5. 테마가 활성화되면 `테마 → 저장 뉴스`를 조회하고, 새 기사가 들어오면 `기사 → 현재 테마`를 역방향으로 매칭한다.
6. 저장된 근거가 없을 때만 서버가 고정 규칙으로 종목명·테마명 보완 검색을 실행한다.
7. LLM은 인터넷 검색을 하지 않는다. 관련성 기준을 통과한 기사의 종목·테마·상승 이유 구조화와 자체 요약에만 사용한다.
8. 관련 기사가 없으면 LLM을 호출하지 않고 `상승 이유 확인 중` 또는 `확인된 신규 소재 없음`으로 표시한다.
9. 사용자에게는 기사 문장을 그대로 차용하지 않고 자체 요약과 매체·발행 시각·원문 링크를 함께 제공한다.
10. 기사 전문은 라이선스나 이용약관이 명시적으로 허용할 때만 처리·저장한다.

### 처리 흐름

```text
RSS·NAVER 특징주 최신순 자동 수집
→ 중복 제거·뉴스 DB 저장
→ 가격·거래량으로 테마 탐지
→ 저장된 뉴스와 테마 양방향 매칭
→ 관련성 기준을 통과한 기사만 LLM 구조화
→ 자체 요약 + 출처 + 시각 표시
```

특징주 기사가 먼저 도착하면 저장해두었다가 이후 감지된 테마와 연결한다. 테마가 먼저 감지되면 기존 저장소를 즉시 조회하고, 이후 새 기사가 도착할 때 다시 연결한다.

### 구성 요소별 책임

| 구성 요소 | 책임 |
|---|---|
| 키움 실시간 시세 | 상승 종목과 동반 움직임 탐지 |
| 뉴스 수집기 | RSS·NAVER 최신순 조회, cursor 관리, 재시도 |
| 뉴스 저장소 | 메타데이터 저장, 중복 제거, 종목·Entity 인덱스 |
| 뉴스-테마 매처 | 시간·종목·테마·동의어 기반 관련성 평가 |
| 서버 보완 검색 | 로컬 근거가 없고 cooldown이 지난 경우만 외부 API 조회 |
| LLM | 선택된 기사에서 상승 이유 구조화·요약 |
| 장후 인포스탁 동기화 | 장중 추정과 확정 사유 비교·수정 이력 유지 |

### 초기 운영 주기

- 특징주 뉴스 수집: 장중 30~60초
- 새 기사 저장 후 활성 테마 역매칭: 이벤트 즉시
- 테마 상태 변화 후 로컬 뉴스 조회: 이벤트 즉시
- 외부 보완 검색: 로컬 근거 없음, cooldown 경과, API 예산 여유를 모두 만족할 때
- LLM 호출: 관련성 기준을 통과한 새 기사-테마 조합에 한정

주기는 고정된 제품 약속이 아니라 공급원 약관·호출 한도·실측 지연을 확인한 뒤 조정할 초기값이다.

### 금지 사항

- LLM에 브라우징 또는 검색 도구를 주어 상승 이유를 직접 찾게 함
- 출처 기사에 없는 인과관계를 LLM의 일반 지식으로 보충함
- 특징주 기사 한 건만으로 테마 상승을 최초 확정함
- 기사 원문을 사용자 화면에 무단 재배포함
- 나중에 발행된 기사를 이전 시점에 이미 알았던 근거처럼 소급 적용함

### 검증 과제

- 원문 발행 시각부터 내부 저장까지의 수집 지연
- 언론사별 특징주 수집 누락률
- URL·제목 중복 제거 정확도
- 뉴스-테마 매칭 정밀도·재현율
- 장후 인포스탁 상승 사유와 장중 자체 요약의 일치율
- LLM 요약의 기사 근거 충실도와 운영자 수정률
- 외부 보완 검색 비율과 LLM 호출량·비용

## PD-004. 인포스탁 자동 수집과 변경 감지

- 상태: 채택
- 결정일: 2026-08-14
- 적용 대상: 국내 테마 목록·상세와 Daily 특징 테마

### 수집 경로

| 데이터 | 수집 방식 |
|---|---|
| 국내 테마 목록 | `POST /web/theme/all` |
| 테마 설명·히스토리·관련 종목 | `POST /web/theme/detail` |
| Daily 특징 테마 | 로그인 세션을 가진 별도 브라우저 worker |

API 서버가 직접 수집하지 않는다. 외부 scheduler가 수집 worker를 실행하고, worker는 원본 snapshot 저장·검증·변경 감지·DB 반영을 수행한다. 중복 실행은 PostgreSQL advisory lock 또는 Redis lock으로 막는다.

### 네이버 연동 로그인과 세션 수명주기

인포스탁 로그인은 네이버 연동 로그인을 사용한다. 서버는 네이버 ID·비밀번호를 환경변수로 저장하거나 자동 입력하지 않는다.

1. 최초 배포 시 운영자가 OCI worker host에서 운영자 전용 인증 명령을 실행한다.
2. 명령은 서버 loopback에만 인증 UI를 열고, 운영자는 SSH tunnel을 통해 화면이 보이는 전용 브라우저에 접속해 네이버 로그인을 직접 완료한다. VNC·noVNC 계열 port는 인터넷에 직접 공개하지 않는다.
3. worker는 인포스탁의 인증 완료 marker를 확인한 뒤 browser context의 storage state를 암호화해 원자적으로 저장하고 브라우저를 종료한다.
4. 정기 수집 때 scheduler는 저장된 state를 복호화해 백그라운드 브라우저에 주입한다. 인증된 페이지 수집이 성공한 경우에만 갱신된 state를 다시 저장한다.
5. state는 컨테이너의 임시 파일시스템이 아니라 암호화된 영구 volume에 보관해 worker 재시작·재배포 뒤에도 복원한다.
6. 세션이 실제로 만료되면 자동 로그인을 시도하지 않고 `AUTH_REQUIRED`로 종료한다. 운영자가 같은 인증 명령의 refresh 모드로 다시 로그인하면 다음 예약 실행부터 정상 수집한다.

세션 유지 기간은 보장하지 않는다. 로그아웃, 비밀번호 변경, 네이버·인포스탁 보안 정책, 서버 환경 변경으로 언제든 만료될 수 있다.

```text
INFOSTOCK_SESSION_STATE_PATH=./.secrets/infostock-storage-state.enc
```

`INFOSTOCK_SESSION_STATE_PATH`에는 암호화된 state 파일 경로만 둔다. 암호화 키는 `APPLICATION_ENCRYPTION_KEY`로 주입하며 state 파일과 같은 저장소에 두지 않는다. production에서는 root 소유 `0600` env 파일 또는 OCI Vault를 사용한다. state·cookie·token은 Git, DB 평문, 원본 snapshot, 기본 로그에 기록하지 않는다.

### 초기 실행 주기

| 작업 | 주기 |
|---|---|
| 테마 목록 확인 | 평일 09:00·13:00·18:30 KST, 주말 18:30 KST |
| 신규·이름 변경 테마 상세 | 목록 변경 감지 직후 |
| 활성 테마 상세 | 매일 18:30 목록 확인 후 |
| 나머지 테마 상세 | 전체를 7개 묶음으로 나눠 하루 한 묶음씩 |
| Daily 특징 테마 | 평일 16:30~23:00 KST에 30분 간격 |
| Daily 누락 보충 | 다음 평일 08:00 KST |

해당 날짜의 Daily 자료가 저장되면 그날 남은 polling은 실행하지 않는다. 게시 시각을 2주간 측정한 뒤 polling 구간을 줄인다.

### 신규·변경 감지

테마 이름이 아니라 `themeId`를 식별자로 사용한다.

```text
처음 보는 themeId                    = THEME_CREATED
기존 themeId의 이름 변경             = THEME_RENAMED
3회 연속 정상 목록에서 themeId 누락  = THEME_INACTIVE
```

- 목록에서 한 번 사라졌다는 이유로 테마나 과거 데이터를 삭제하지 않는다.
- 신규·이름 변경 테마는 즉시 상세 수집 대상으로 넣는다.
- 원본 응답과 정규화 결과의 hash가 같으면 DB revision을 추가하지 않는다.
- 모든 적재는 재실행해도 결과가 중복되지 않는 upsert로 처리한다.

### `401`·`403` 재시도

인포스탁에서는 일시적 호출 제한이 `401` 또는 `403`으로 나타날 수 있으므로 첫 응답만으로 로그인 만료를 확정하지 않는다.

1. 진행 cursor와 `next_retry_at`을 저장하고 작업을 `RATE_LIMITED`로 종료한다.
2. 10분 후 재실행하고 다시 실패하면 30분, 이후 60분 간격으로 재실행한다.
3. 성공하면 마지막 완료 지점부터 `resume`하고 backoff를 초기화한다.
4. 수집은 단일 worker와 요청 간 최소 2초 간격을 기본값으로 사용한다.
5. `Retry-After`가 있으면 자체 backoff보다 해당 값을 우선한다.

worker 프로세스가 대기 상태로 잠들지 않는다. scheduler가 `next_retry_at` 이후 새 작업을 실행한다.

### 로그인 만료 판정

다음 중 하나를 확인했을 때만 Daily 수집을 `AUTH_REQUIRED`로 전환한다.

- 브라우저 최종 URL이 로그인 페이지임
- 로그인 화면이 반환되고 인증된 화면 marker가 없음
- 저장된 state 복원과 제한된 재시도 후에도 같은 인증 실패가 반복됨

HTTP `200`이어도 로그인 화면이면 인증 실패다. `AUTH_REQUIRED` 상태에서는 예약된 Daily 수집과 반복 로그인을 중단하고 작업 상태와 기본 로그에 원인을 기록한다. 마지막 정상 state를 로그인 페이지의 state로 덮어쓰지 않는다. 이메일·SMS·Web Push 같은 외부 알림은 보내지 않는다.

### 작업 상태

```text
RUNNING
SUCCEEDED
PARTIAL
RATE_LIMITED
AUTH_REQUIRED
FAILED
```

각 실행은 `runId`, 시작·종료 시각, 처리 cursor, 성공·실패 건수, 응답 hash, `next_retry_at`을 저장한다.

## PD-006. 모든 제품 데이터는 Google 로그인 후 제공

- 상태: 채택
- 결정일: 2026-08-14
- 적용 대상: Web 화면, REST API, WebSocket

### 결정

1. 비로그인 사용자는 로그인 화면만 볼 수 있다.
2. 오늘·인사이트·테마·뉴스·유사사례를 포함한 모든 제품 화면과 데이터 API는 Google 로그인 session을 요구한다.
3. 로그인 정적 화면, Google OAuth endpoint, logout, 필수 정적 문서와 제품 데이터를 포함하지 않는 최소 health check만 비로그인 접근을 허용한다.
4. 인증은 서버가 발급한 Secure·HttpOnly host-only cookie session을 사용하고 Vercel app origin의 `/api/*` rewrite로 OCI에 전달한다.
5. 비로그인·만료 session의 REST 요청은 제품 데이터 없이 `401 AUTHENTICATION_REQUIRED`, WebSocket handshake는 snapshot 전송 전에 거부한다.
6. 로그인 성공 후 `APP_BASE_URL` 기준 내부 `returnTo`만 허용하고 검증 실패 시 `오늘`로 이동한다.
7. session 만료와 로그아웃 때 브라우저의 제품 cache·메모리 snapshot을 폐기한다.

### 이유

- 모든 데이터 접근 경로에 동일한 인증·rate limit·entitlement 기준을 적용한다.
- 이후 유사사례 pilot과 운영자 권한을 사용자 session 위에 명확히 분리한다.
- 비로그인 cache와 인증 후 cache가 섞여 데이터가 남는 문제를 막는다.

### 검증

- [ ] 비로그인 상태에서 직접 URL, REST, WebSocket으로 제품 데이터에 접근할 수 없다.
- [ ] 로그인 성공 후 원래 내부 화면 또는 오늘 화면으로 이동한다.
- [ ] open redirect가 차단된다.
- [ ] session 만료와 로그아웃 후 화면·cache·WebSocket 데이터가 제거된다.
- [ ] 일반 사용자가 operator endpoint에 접근할 수 없다.

## PD-007. Google 계정에 관심 테마·종목·이벤트를 저장

- 상태: 채택
- 결정일: 2026-08-14
- 적용 대상: 사용자별 데이터, 관심 화면, 계정 삭제

### 결정

1. 사용자는 테마, 종목, 접근 가능한 현재·과거 이벤트를 저장·해제할 수 있다.
2. 저장 항목은 Google 계정에 연결해 session과 기기가 달라도 동기화한다.
3. 관심 화면은 전체·테마·종목·이벤트 필터, 저장 시각, 현재 상태, 최근 변경과 원래 상세 화면 이동을 제공한다.
4. 동일 사용자·동일 대상의 저장은 하나만 유지하고 저장·해제 mutation은 idempotent하게 구현한다.
5. 저장 여부는 공용 테마 순위·실시간 계산·유사사례 score에 영향을 주지 않는다.
6. 대상이 비활성·삭제·권한 제한이면 다른 대상으로 조용히 바꾸지 않고 사용 불가 이유를 표시한다.
7. 사용자는 자기 저장 데이터와 계정을 삭제할 수 있다. 삭제 시 모든 session, 최소 프로필과 저장 항목을 제거한다.
8. 이메일·SMS·Web Push 알림, 자동매매, 증권계좌·보유종목·주문 연동은 구현하지 않는다.

### 보안·데이터 규칙

- API는 request의 임의 `userId`를 받지 않고 인증 session에서 소유자를 결정한다.
- 사용자 간 저장 데이터 조회·수정이 불가능하도록 소유권 검사를 모든 query와 mutation에 적용한다.
- Google access token·refresh token은 저장 기능에 사용하지 않는다.
- 브라우저 local storage는 관심 데이터의 기준 저장소가 아니다.

### 검증

- [ ] 테마·종목·이벤트 저장·해제가 재시도에 안전하다.
- [ ] 다른 로그인 session과 기기에서 동일한 저장 목록이 보인다.
- [ ] 다른 사용자의 target ID나 saved ID를 추측해도 접근할 수 없다.
- [ ] 사용 불가 대상의 정체성과 저장 기록을 조용히 변경하지 않는다.
- [ ] 계정 삭제 후 session·프로필·저장 데이터가 남지 않는다.

## PD-008. 운영자 콘솔은 일반 사용자와 완전히 분리

- 상태: 채택
- 결정일: 2026-08-14
- 적용 대상: 운영 화면, 운영자 API, 역할·감사 기록

### 접근 결정

1. 내부 운영자 콘솔은 허용된 Google 계정의 `OPERATOR` 역할만 접근한다.
2. 일반 사용자 navigation·검색·sitemap·route 안내에는 운영자 진입점을 표시하지 않는다.
3. client route 숨김을 권한으로 사용하지 않는다. 일반 사용자 session의 `/v1/operator` 요청은 서버에서 `403`으로 거부한다.
4. 최초 운영자는 배포 설정의 verified Google email로 bootstrap한 뒤 내부 사용자 ID와 Google `sub`에 `OPERATOR` 역할을 연결한다.

### 구현 범위

- 키움·뉴스·인포스탁 수집 상태와 마지막 성공 시각
- 실패 작업 목록과 허용된 retry·resume
- 인포스탁 `AUTH_REQUIRED` 상태와 OCI loopback + SSH tunnel 재인증 runbook
- 장중·장후 분류 불일치, 뉴스 근거, 미매칭 Event 검수
- 분류 수정·병합·제외와 revision·audit 이력
- 기본 process 상태와 배포 version

### 금지 범위

- 일반 사용자 API에 `reviewStatus`, 담당자, 내부 사유·메모 포함
- 브라우저 기반 서버 terminal·파일 브라우저·임의 SQL
- secret·cookie·token·SSH private key·네이버/키움 credential 원문 표시·수정
- 인포스탁 인증 UI 또는 VNC·noVNC public port 노출
- 원본 row hard delete·덮어쓰기

### Command 규칙

- 모든 mutation은 CSRF 방어, idempotency key, 현재 version과 운영자 사유를 요구한다.
- 수행자, 시각, 대상, 사유, 이전/이후 revision과 결과를 audit에 기록한다.
- 이미 완료된 작업과 stale version은 조용히 재실행하지 않고 명시적으로 거부한다.

### 검증

- [ ] 일반 사용자 계정과 직접 URL 요청에서 운영 화면·API·field가 노출되지 않는다.
- [ ] 운영자만 상태 조회·retry·resume·검수 command를 수행한다.
- [ ] 모든 command에서 audit ID와 이전/이후 revision을 확인할 수 있다.
- [ ] 운영자 화면·API·로그 어디에도 비밀정보 원문이 없다.
- [ ] 인포스탁 수동 재인증이 public port 없이 동작한다.

## PD-009. 유동주식 기준정보는 무료 공식 API 범위에서만 확보

- 상태: 채택
- 결정일: 2026-08-14
- 적용 대상: 현재 테마 수익률 기준정보, 외부 데이터 비용·계약

### 결정

1. 유동주식 기준정보를 위해 KRX 유료 데이터상품, 지수정보상품 또는 상용 데이터 공급원을 계약·구매하지 않는다.
2. KRX 연동은 KRX Open API 인증키로 사용할 수 있는 무료 공식 API 범위까지만 허용한다.
3. 금융감독원 OpenDART의 무료 공식 API를 KRX Open API의 보완 원천으로 사용한다.
4. 공개 API 응답 필드의 의미·대상 종목 Coverage·기준일을 실제 표본으로 검증한 뒤 사용한다.
5. 공개 API에서 검증된 유동주식비율을 확보하지 못하면 총시가총액이나 자기주식 제외 시가총액으로 조용히 대체하지 않는다.
6. KRX·OpenDART 원천을 조합한 자체 산출은 원천별 정의, 기준일, 제외 규칙과 재현 테스트를 고정한 뒤 사용한다.

### DAYJAVIEW 유동주식비율 정의

이 값은 KRX 유료 지수정보상품의 공식 유동비율과 동일하다고 주장하지 않는다. 무료 공식 원천만으로 동일 입력에서 같은 결과를 재현할 수 있는 DAYJAVIEW의 기준정보다.

```text
DAYJAVIEW 유동주식수
= 발행 보통주식수
  - 중복을 제거한 확인 가능 비유동 보통주식수

DAYJAVIEW 유동주식비율
= DAYJAVIEW 유동주식수 / 발행 보통주식수
```

확인 가능 비유동 지분에는 자기주식, 최대주주·특수관계인 보유분, 공식 공시에서 식별되는 보호예수·전략 보유분을 포함한다.

- 보유자 식별자·주식 종류·기준일을 사용해 같은 지분의 중복 차감을 막는다.
- 계산 시점 이전에 공개된 최신 원천만 사용하고 미래 공시를 소급 적용하지 않는다.
- KRX 발행주식수와 OpenDART 보고서 기준이 충돌하거나 중복 여부를 해결할 수 없으면 해당 종목을 계산에서 제외한다.
- 원본 응답, 공시 접수번호, 기준일, 적용일, 산출 버전과 제외 사유를 저장한다.

### 구현 영향

- 기준정보 모듈에 KRX Open API·OpenDART adapter와 원본 snapshot 저장을 둔다.
- 운영 비밀값은 `KRX_API_KEY`, `OPENDART_API_KEY`로 주입하고 Git·로그·브라우저에 노출하지 않는다.
- 유동주식비율이 검증되지 않은 종목은 테마 수익률 Coverage에서 제외한다.
- 전체 대상 Coverage가 출시 기준에 미달하면 테마 수익률 기능의 출시 게이트는 통과하지 못한다.
